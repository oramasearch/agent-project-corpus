# agent-project-corpus v0.1.0

**Released 2026-10-17. The first release.** One Python package, `agent-project-corpus`, and one
private image, `docker.io/oramasearch/agent-project-corpus:v0.1.0`. It is the **Project Corpus
Agent**, one of Lake's library agents.

It generates training examples for the Project Agent: tool-calling trajectories that build and run
a catalogue Solution, or create or change (`mutate`) a methodology Pipeline. Every observation in
an example is replayed against a real workspace instead of being written by the model. It runs in
two ways:

- **In Lake**, as a service: a person asks (through Ask Orama) for a worked example on their own
  data. One turn records one example on that workspace and returns it in the answer. Nothing is
  added to the corpus.
- **Offline**, as a batch command line that appends kept examples to `corpus/project-sft-v1.jsonl`.

Proprietary to Orama; private repository and image.

## What it includes

### Prompt

- `PROMPT_VERSION = "v3"` (`src/agent_project_corpus/agent.py`), read from
  `src/agent_project_corpus/prompts/v3.md`. Prompts `v1.md` and `v2.md` are kept for provenance
  and are not used.
- `CORPUS_VERSION = "v1"`: the batch command line writes `corpus/project-sft-v1.jsonl`. Every
  record carries its own `prompt_version`.
- Example kinds: `solution`, `create` and `mutate`. A `mutate` example carries `before`, the
  pipeline as it was.

### The generation checks

- **Solutions first.** Each turn reads `list_solutions`. If it returns entries, the turn is a
  `solution` turn:
  - the example may choose only an entry the live response marks runnable;
  - `get_solution` reads that entry again, and a sketch or non-runnable entry is rejected with its
    promotion condition or issue;
  - the trajectory must start with `list_solutions`, read `get_solution`, and end with
    `create_solution {project, solution, level, sources}`, at a level the entry offers.
- **Methodologies otherwise.** With no solution entries, the turn reads `list_methodologies`:
  - only a `runnable` entry whose `model_kinds` contain the example's `model_kind` is accepted;
  - the trajectory must call `compile_intent` with that methodology.
  - If `list_methodologies` answers `unknown_capability`, only the legacy M-1 GBDT classifier is
    allowed, and the reply says the fallback was used.
- **The `because` chain.** Every call after the first must name an earlier call whose
  observation justified it (`defects` in `agent.py`).
- **Replay** (`replay` in `node.py`): the written observations are replaced by what the workspace
  returned.
  - Reads replayed: `list_solutions`, `get_solution`, `get_policy`, `get_experiment`,
    `list_ledger`, `get_monitor`, `get_roi_readout`, `list_datasets`, `get_dataset`,
    `list_models`, `get_model`, `list_projects`, `get_project`, `model_health`,
    `list_connections`, `list_indexes`.
  - Actions replayed: `compile_intent`, `create_solution` and `run_solution`.
  - After `compile_intent`, replay calls `run` with the compiled graph and the dataset read by
    `get_dataset`.
  - After `create_solution`, replay calls `run_solution` on the returned project and graph. After
    a successful run it reads `get_policy`, `get_experiment`, `list_ledger`, `get_monitor` and
    `get_roi_readout`. Any of these five that answers `unknown_capability` is recorded as
    `not_deployed_yet`.
  - A failed call is kept as a failed observation and rejects the example.
- **The recorded solution result.** A kept solution example stores `pipeline`, `run`,
  `operations` and `readout`. It also stores a `policy_proposal` and `label_definitions` derived
  from the live `get_solution` entry, both marked for owner sign-off. A readout is measured
  evidence, never a promised ROI figure.
- **The recorded methodology result:** `compiled_pipeline` (the engine's graph, also stored as
  `pipeline`) and `run`. A compiled graph for another methodology or model kind, a `structural`
  run, or a failed or cancelled run rejects the example.

[Solutions](../solutions/README.md), [methodologies](../methodologies/README.md).

### The service (`agent-project-corpus-serve`)

A standard-library HTTP server on `PORT` (default 8080), in `service.py`:

| Route | What it does |
|---|---|
| `GET /healthz` | `{ok, agent: "agent-project-corpus", version, prompt_version}`; `version` is the installed package version |
| `POST /v1/turn` | Runs one turn and answers 200 `{ok: true, reply, result: {kind: "project_example", example}}`, or 422 `{ok: false, error}`. With `AGENT_SERVICE_TOKEN` set, it requires `Authorization: Bearer <token>` (401 otherwise); a body that is not JSON is a 400 |

The turn body (`run_turn`):

| Field | Meaning |
|---|---|
| `request` (or `message`) | What the person asked. Words such as "change", "modify", "edit", "update" or "existing" ask for a `mutate` example in a methodology turn; otherwise `create` |
| `zetta_base_url`, `zetta_token` | The person's workspace, through Lake's workspace route, with the task's credential. Required |
| `lake_url`, `lake_token` | Lake's model gateway and the task's credential, used as the model's API key. `LAKE_URL` is the fallback for the address and `zetta_token` for the key |

The turn:
1. reads the solution or methodology registry;
2. reads `list_datasets`, and refuses a workspace with no datasets;
3. asks the model for one example whose profile is that workspace's tables (up to 12);
4. checks the example and replays it as above.

No dataset is landed (`land_profile` is not used in a turn).

**The model is reached through Lake** (lake#248; `model.py`). Every model call of a turn goes to
`<lake_url>/openai/v1` with the turn's credential as the API key, so Lake counts the tokens in the
turn's workspace. The service holds no provider key.

### The agent bus (`lake_bus.py`)

When `LAKE_URL`, `AGENT_BUS_TOKEN` and the agent name are all set, `serve` starts one background
thread that takes tasks from Lake. Every call goes to Lake at `<LAKE_URL>/v1/<capability>`, with
`AGENT_BUS_TOKEN` as the bearer:

1. `receive_agent_tasks {agent, from_sequence, wait_ms: 10000}`: a long poll, starting at sequence
   1 when the process starts.
2. `claim_agent_task {task_id, agent}` for each task. A `conflict` or `not_found` means another
   replica has it and is skipped. The claim's answer is the task with its `body`, in which Lake has
   put the task's credential as `lake_token` and `zetta_token`.
3. The body is run as a turn, up to 4 at once, in a thread pool.
4. `publish_agent_event`: `progress` ("Working on it"), then `result` with the whole answer, or
   `failed` with the error. A turn that raises is reported as `failed`; the worker keeps running.

A failed receive is logged and retried after 2 seconds. Without the bus configuration the service
logs `bus: not configured` and serves HTTP only. The bus calls send no `workspace_id`, and the agent sends no
heartbeat; Lake renews the lease on each capability call made with the task credential. Lake protocol:
[lake `docs/api/agent-bus.md`](https://github.com/oramasearch/lake/blob/dev/docs/api/agent-bus.md).

### The batch command line (`agent-project-corpus`)

`agent-project-corpus [--examples N] [--model M] [--out DIR]` (defaults: 5, `PROJECT_CORPUS_MODEL`
or `gpt-4o`, `corpus`).

- It refuses to run (exit code 2) without `ZETTA_BASE_URL` and `ZETTA_TOKEN`.
- It calls OpenAI directly with the caller's own `OPENAI_API_KEY`; this is the only path that
  does.
- Methodology turns alternate `create` and `mutate`. Each profile's tables are landed on the node
  with `add_dataset` (null fractions honoured) before replay.
- Kept examples are appended to `<out>/project-sft-v1.jsonl`, and the run prints its kept and
  rejected counts.

### The corpus

`corpus/project-sft-v1.jsonl` holds 23 examples: 14 `mutate`, 9 `create`. All 23 were generated
with prompt v1, and only one is marked `observations_real`. [`corpus/README.md`](../../corpus/README.md)
describes it.

The corpus is not copied into this repository's image. It is the `corpus` named build context of
the `agent-project` image, which copies `project-sft-v1.jsonl`.

This agent does not read them in a turn.

### The image

`oramasearch/agent-project-corpus` on Docker Hub, **private** (`Dockerfile`):
- a `python:3.12-slim` build stage that installs the locked environment with uv 0.11.7
  (`uv sync --frozen --no-dev --no-editable`);
- a `python:3.12-slim` runtime with only `/app/.venv`, run as user `10001`, exposing 8080, with
  entry point `agent-project-corpus-serve`.

It needs no named build contexts. The prompts ship inside the package; `corpus/` is not in the
image.

## How Lake reaches it

- **The operator runs it** as a Lake library agent: one Deployment and one Service per Lake, port
  8080, probed on `/healthz`. The pod gets `LAKE_URL`, `AGENT_SERVICE_TOKEN`, its own
  `AGENT_BUS_TOKEN` from the Secret `lake-<name>-agent-bus`, and `AGENT_BUS_AGENT=agent-project-corpus`.
- **Lake learns its address** from `LAKE_AGENT_ENDPOINTS` (`agent-project-corpus=<url>`). Lake's
  catalogue lists it as the *Project Corpus Agent*.
- **A turn is dispatched over the agent bus.**
  - Lake writes the request to the task's workspace Zetta and publishes only
    `{task_id, customer_id, workspace_id, agent, kind}` on `agent-tasks.agent-project-corpus` on
    Lake's own Zetta; the bus carries task ids, never content.
  - The agent takes and answers the task through Lake as described above.
  - Lake's task carries `request`, `lake_url`, `lake_token`, and `zetta_base_url` (Lake's
    workspace route) with `zetta_token`.

## What it does not include

- **Training.** Nothing has been trained on this corpus; it has no evidence yet that it teaches
  what it intends to.
- **A corpus to train on.** 23 examples, written with prompt v1, before replay existed. Only one
  example's observations were returned by a real node (zetta#989).
- **Adding a Lake turn's example to the corpus.** A turn returns its example and stores nothing.
- **Multi-turn trajectories.** An example is one ask and its calls.
- **An offline evaluation.** Every generation path needs a live model and a live workspace.
- **Usage reporting of its own.** Lake's model gateway counts a turn's tokens.

## Known issues

Security-relevant first.

1. **Workspace identity is not passed explicitly**
   ([agent-project-corpus#6](https://github.com/oramasearch/agent-project-corpus/issues/6)). The
   agent sends no `workspace_id` on its bus calls and relies on the task credential to choose the
   workspace. It also has no idle backoff: an idle agent long-polls continuously instead of at most
   once a minute.
2. **A Lake turn replays write actions, but Lake gives this agent a read-only credential.**
   Found while writing these notes, by reading the code; not observed live. [agent-project-corpus#8](https://github.com/oramasearch/agent-project-corpus/issues/8).
   - Replay calls `compile_intent`, `run`, `create_solution` and `run_solution` on the person's
     workspace.
   - Lake grants this agent's task only `workspace_query`, `workspace_openapi` and
     `get_agent_task`, and describes the agent as changing nothing.
   - So in Lake these actions are expected to be refused, and the turn rejected.
   - If they were allowed, a turn would create a project and graph and run them in the person's
     workspace.
   - The Dockerfile's comment ("it lands and writes nothing") holds only for datasets.
3. **`POST /v1/turn` accepts the workspace and gateway addresses from its caller.**
   - Anyone holding `AGENT_SERVICE_TOKEN` can make it send a bearer token to any URL; Lake's docs
     say user-created agents on agent-runtime hold that token too.
   - With the variable unset, the route is open; the operator always sets it.
   - [agent-project-corpus#9](https://github.com/oramasearch/agent-project-corpus/issues/9).
4. **The lease is kept by activity only.** The agent sends no heartbeat of its own. Lake renews a claim's lease on every accepted event and every capability call made with the task credential (lake [`docs/api/agent-bus.md`](https://github.com/oramasearch/lake/blob/dev/docs/api/agent-bus.md)), so a turn can be reclaimed only if a single step between two such calls, such as one model call, outlasts `lease_seconds` (600 seconds by default). Not observed. If it happens, the first terminal event wins.
5. **The bus restarts from sequence 1** on every process start. Already-claimed tasks are filtered
   by Lake and losing claims are skipped.
6. **The committed corpus predates prompt v3 and replay**
   ([zetta#989](https://github.com/oramasearch/zetta/issues/989)). 22 of its 23 examples carry
   observations the model wrote. `corpus/README.md` says 22 examples, but the file has 23.
